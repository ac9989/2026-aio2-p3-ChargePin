# 서울 전기차 충전 및 주차 안내 서비스 기획서

> 서비스명: 미정  
> 작성일: 2026-11-04 (KST)

## 1. 프로젝트 개요

서울에서 전기차를 이용하는 사용자가 충전소와 주차장을 찾을 때, 지도·필터·자연어 채팅으로 조건을 입력하면 장소 후보와 상태 정보를 한 화면에서 안내하는 서비스다.

이 서비스는 장소를 단순히 나열하지 않는다. 카카오 지도/장소 API는 위치와 장소 후보에, 서울시 시영주차장 데이터는 주차 현황에, 환경공단 API는 충전기 상태에 각각 사용한다. 각 정보에는 출처와 갱신 시각을 표시하며, 지연되거나 검증되지 않은 정보는 확정적으로 안내하지 않는다.

## 2. 기획 배경과 문제 정의

전기차 사용자는 충전 가능 장소뿐 아니라 주차 가능 여부, 충전기 타입, 이동 거리까지 함께 고려해야 한다. 그러나 장소 검색, 주차 현황, 충전기 상태가 서로 다른 서비스와 데이터에 분산돼 있어 빠르게 판단하기 어렵다.

특히 지도에서 확인한 충전소나 주차장이 실제로 이용 가능한지 즉시 알기 어렵고, 공공 실시간 데이터도 제공 갱신 시각과 실제 현장 상태 사이에 차이가 있을 수 있다. 이를 숨기고 "이용 가능"이라고 단정하면 사용자의 이동 시간과 서비스 신뢰를 잃을 수 있다.

이 프로젝트는 여러 출처를 하나로 연결하되, 데이터의 한계를 투명하게 보여 주는 전기차 이동 지원 서비스를 목표로 한다.

## 3. 목표 사용자

| 사용자             | 상황                                                            | 필요한 가치                                     |
| ------------------ | --------------------------------------------------------------- | ----------------------------------------------- |
| 일반 전기차 운전자 | 목적지 주변에서 충전·주차 위치를 빨리 찾아야 함                 | 지역·반경·충전기 타입별 빠른 탐색               |
| 목적지 방문자      | 익숙하지 않은 서울 지역에서 주차와 충전을 함께 고려해야 함      | 지도 중심의 위치 안내와 출처가 명확한 상태 정보 |
| 운영 관리자        | 외부 API 지연·오류, 데이터 품질, 사용자 차단 요청을 관리해야 함 | 재시도·캐시·장애·가드레일·배포 현황 확인        |

## 4. 서비스 목표

1. 서울 중심 전기차 충전소와 주차장 후보를 지도와 검색 조건으로 빠르게 탐색하게 한다.
2. 충전기 상태와 주차 현황을 출처·갱신 시각과 함께 안내한다.
3. 자연어 채팅과 직접 입력을 같은 검색 기준으로 연결해 결과의 일관성을 보장한다.
4. 데이터 지연·누락·이상값을 숨기지 않고 안전하게 표시한다.
5. 외부 API·LLM 장애와 권한 요청을 역할 분리, 가드레일, 감사 이력으로 통제한다.

## 5. 핵심 기능

### 5.1 지도와 사이드바 검색

- 사용자는 지도에서 중심 위치를 선택하거나 지역을 고른다.
- 충전기 타입과 검색 반경 1 km, 3 km, 5 km를 선택한다.
- 서비스는 반경 5 km 초과 요청을 UI와 서버에서 모두 차단한다.
- 충전소·주차장 후보를 지도 핀과 목록 카드로 제공한다.

### 5.2 자연어 채팅 검색

사용자는 “강남역 근처 3 km 안에서 급속 충전 가능한 곳과 빈 주차장을 알려줘”처럼 말할 수 있다.

Planner는 이 요청을 지역, 중심 위치, 충전기 타입, 반경, 검색 대상으로 구조화한 조건 카드로 바꾼다. 사용자가 조건을 확인한 뒤에만 검색이 실행된다. 따라서 사용자가 의도하지 않은 조건으로 외부 API를 호출하거나 결과를 단정하지 않는다.

### 5.3 출처 기반 상태 안내

| 정보             | 사용 출처               | 표시 원칙                                                |
| ---------------- | ----------------------- | -------------------------------------------------------- |
| 지도와 장소 후보 | 카카오 지도/장소 API    | 위치·이름·주소·지도 후보로만 사용                        |
| 시영주차장 현황  | 서울시 실시간 데이터    | 총면수·현재 차량 수·갱신 시각을 표시                     |
| 빈자리           | 서울시 주차장 수치 계산 | `총 주차면 - 현재 차량 수`, `마지막 보고 기준` 문구 필수 |
| 충전기 상태      | 환경공단 API            | 제공 상태·충전기 타입·갱신 시각을 표시                   |

카카오 장소 후보만 있는 경우에는 장소는 표시할 수 있지만 빈자리나 충전 가능 상태를 추정하지 않는다. 서울시 데이터가 오래됐거나 수치가 비정상인 경우에도 해당 주차장을 숨기지 않고 `정보 지연` 또는 `확인 불가`로 표시한다.

### 5.4 운영 대시보드

운영 대시보드는 다음 정보를 한 화면에서 제공한다.

- 카카오·서울시·환경공단 API의 성공률, 오류, 지연, 마지막 성공 시각
- Planner·Executor·Critic의 성공률, 재시도 횟수와 최종 판정
- stale, 누락, 비정상 주차 수치, 시설 매칭 불확실성 등 데이터 품질 현황
- 입력·출력 가드레일과 권한 차단 수
- 캐시 폴백, Circuit Breaker, 장애와 복구 이력
- GitHub Actions, Docker 이미지, GHCR, AWS EC2 Docker Compose 배포 상태와 배포 차단 사유

## 6. 차별점

### 6.1 장소 정보와 상태 정보를 구분하는 설계

장소 후보를 찾는 API와 실시간 상태를 제공하는 API는 역할이 다르다. 본 서비스는 이 차이를 사용자 화면에도 유지한다. 카카오 데이터가 장소를 찾는 근거라면, 주차 수치는 서울시 데이터, 충전 상태는 환경공단 데이터가 근거가 된다.

### 6.2 정보의 최신성을 숨기지 않는 결과

사용자에게 가장 위험한 것은 오래된 수치를 현재 정보처럼 보이게 하는 일이다. 모든 상태 카드에는 갱신 시각을 표시하고, 오래된 데이터·누락 데이터·비정상 수치는 확정 수치 대신 안전한 안내 문구로 바꾼다.

### 6.3 멀티 에이전트 역할 분리

| 논리 역할     | 핵심 책임                                             |
| ------------- | ----------------------------------------------------- |
| Planner       | 자연어를 확인 가능한 `SearchRequest`로 구조화         |
| Executor      | 허용된 출처 API를 호출하고 결과를 정규화              |
| Critic        | 최신성·이상값·출력 규칙을 독립 검증하고 재시도를 요청 |
| Memory Keeper | 세션·중간 결과·재시도·감사 이력을 보존                |

역할을 나누면 한 구성요소가 자연어 해석, 외부 데이터 조회, 품질 판정, 이력 관리까지 모두 맡아 잘못된 결론을 내리는 위험을 줄일 수 있다.

### 6.4 장애에도 신뢰를 유지하는 방식

한 출처가 timeout 또는 오류가 나도 나머지 정상 출처의 결과는 보여 준다. 일시 오류만 제한적으로 재시도하고, 반복 실패한 출처는 Circuit Breaker와 캐시 폴백으로 격리한다. 캐시 결과도 실시간 데이터로 가장하지 않고 원래 갱신 시각과 정보 지연 상태를 표시한다.

## 7. 사용자 이용 흐름

```text
사용자 조건 입력
  ├─ 사이드바: 지역·타입·반경을 직접 선택 → 검색
  └─ 채팅: 자연어 입력 → 조건 카드 확인 → 검색
                         ↓
Executor가 카카오·서울시·환경공단 데이터 수집·정규화
                         ↓
Critic이 최신성·이상값·출처·출력 규칙 검증
                         ↓
정상 결과 또는 정보 지연/확인 불가 결과 표시
                         ↓
Memory Keeper가 요청·결과·재시도·감사 이력 보존
```

## 8. 운영 및 보안 계획

### 8.1 사용자와 관리자 권한

| 역할        | 권한                                                           |
| ----------- | -------------------------------------------------------------- |
| 일반 사용자 | 채팅과 조회만 가능                                             |
| 관리자 3    | 읽기 전용 운영 대시보드 조회                                   |
| 관리자 2    | 실패 건 재처리, 제한된 캐시 갱신, 운영 대시보드 조회           |
| 관리자 1    | 재시도 1/2/3회 정책 설정, 관리자 2/3 승급·강등, 정책·감사 조회 |

관리자 1은 자기 자신의 역할을 변경할 수 없고, 마지막 관리자 1을 제거할 수도 없다. 어떤 역할도 API 키 원문을 볼 수 없다.

### 8.2 가드레일

- 입력 스키마와 최대 반경을 서버에서 검증한다.
- 프롬프트 인젝션, 시스템 지시 덮어쓰기, 채팅을 통한 관리자 기능 요구를 차단한다.
- Planner·Critic·Memory Keeper에는 외부 데이터 API 도구를 주지 않고 Executor만 허용목록 API를 호출한다.
- 결과에는 출처와 갱신 시각을 강제하고, 비정상 데이터는 안전 응답으로 치환한다.
- 모든 차단·정책 변경·운영 행동은 감사 이력으로 남긴다.

## 9. 기술 및 구현 계획

| 단계 | 주요 작업                                                                                             | 산출물                        |
| ---- | ----------------------------------------------------------------------------------------------------- | ----------------------------- |
| P3-1 | SearchRequest/Handoff, 역할 경계, 품질·RBAC·운영 정책 설계                                            | 멀티 에이전트 아키텍처 설계서 |
| P3-2 | Docker Compose/AWS EC2 기반 서비스, healthcheck, Watchdog, Circuit Breaker, 오류 메트릭, 자동 복구 | 배포 및 장애 복구 보고서      |
| P3-3 | Test API, Test Checker, 프런트/백엔드 RBAC·가드레일·복구 테스트, GitHub Actions 배포 게이트           | 파이프라인 구현 결과 보고서   |

P3-3의 배포 흐름은 `test → Docker build → GHCR → AWS EC2 Docker Compose 배포 → 스모크 검증` 순서다. 테스트가 실패하면 뒤 단계가 실행되지 않으며, 결과는 Slack 등의 알림 채널과 운영 대시보드에 남긴다.

## 10. 성공 기준

| 관점        | 성공 기준                                                                                       |
| ----------- | ----------------------------------------------------------------------------------------------- |
| 검색 경험   | 채팅과 사이드바가 동일한 조건 계약으로 검색하고, 반경 제한을 지킨다.                            |
| 데이터 신뢰 | 상태 결과에 출처·갱신 시각이 있으며, stale·누락·이상값에서 가용성을 추정하지 않는다.            |
| 역할 분리   | Planner가 출처 API를 호출하지 않고 Executor만 조회하며 Critic이 독립 검증한다.                  |
| 운영 통제   | 요청 ID, 사용자 역할, 실행 계획, 결과, 재시도, Critic 판정이 감사 가능하다.                     |
| 장애 격리   | 한 출처 오류가 전체 검색 실패로 번지지 않고, 재시도·캐시·Circuit Breaker 상태를 확인할 수 있다. |
| 배포 품질   | 테스트 실패 시 Docker 이미지 빌드 및 AWS EC2 Docker Compose 배포가 차단된다.                  |

## 11. 주요 위험과 대응

| 위험                                | 대응                                                                             |
| ----------------------------------- | -------------------------------------------------------------------------------- |
| 공공데이터 갱신 지연                | 마지막 보고 기준·갱신 시각·정보 지연 상태를 명확히 표시                          |
| 장소와 상태 데이터의 시설 매칭 오류 | 공급자 ID 우선, 이름·주소·좌표를 보수적으로 확인하고 불확실하면 별도 시설로 표시 |
| 외부 API timeout·오류               | 출처별 timeout, 제한 재시도, Cache, Circuit Breaker로 격리                       |
| LLM의 조건 해석/출력 오류           | 사용자 조건 확인, 구조화 출력 계약, 출력 가드레일                                |
| 관리자 권한 오남용                  | 서버 capability 검사, 마지막 관리자 1 보호, 감사 로그                            |
| API 키 유출                         | Docker 이미지·로그·Handoff에 비밀 제외, 런타임 시크릿 주입                       |

## 12. 향후 확정 사항

- 최종 서비스명
- 실제 카카오·서울시·환경공단 API의 필드·호출 한도·갱신 주기
- freshness, timeout, 캐시 TTL, Circuit Breaker 임계치, rate limit 수치
- 인증 방식과 위치·대화·감사 로그 보존 기간
- AWS EC2 Docker Compose 배포 환경과 알림 채널

이 항목들은 실제 API 표본과 테스트 결과를 확인한 뒤 확정한다. 확정 전에는 실시간성이나 빈자리 정확도를 과도하게 약속하지 않는다.
