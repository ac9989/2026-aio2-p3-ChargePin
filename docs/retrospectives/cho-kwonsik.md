## 맡은 역할

ChargePin 프로젝트에서 DevOps 및 서비스 배포를 담당하였다.
주요 업무는 GitHub 저장소 관리, Docker 기반 실행 환경 구성, GitHub Actions를 활용한 CI/CD 파이프라인 구축, AWS EC2 서버 배포 및 운영 환경 점검이었다.
또한 서비스 장애 감지와 복구 기능을 검증하고, 팀원들이 개발한 Frontend와 Backend가 실제 배포 환경에서 정상적으로 연동되는지 확인하였다.
프로젝트 후반에는 테스트 시나리오 66건의 실행 결과와 증빙을 정리하고, 발견된 오류의 수정 및 재검증 과정에도 참여하였다.

## 어려웠던 점

로컬 환경에서 정상적으로 작동하는 서비스가 실제 배포 환경에서도 동일하게 작동하도록 만드는 과정이 가장 어려웠다.
Docker 컨테이너가 실행 중이더라도 서비스가 정상적으로 제공되는 것은 아니었다. 컨테이너 상태, 포트 연결, Health Check, Nginx 프록시 설정 등을 각각 확인해야 했으며, 문제가 발생했을 때 어느 부분이 원인인지 파악하는 데 어려움이 있었다.
GitHub Actions에서 테스트와 빌드가 성공하더라도 실제 운영 화면에서 일부 기능이 정상적으로 작동하지 않는 경우도 있었다. 특히 로그인 직후 기본 검색, 관리자 운영 기능, AI 챗봇의 검색 확인 절차 등에서 문제가 발견되었다.
또한 장애를 감지한 것과 실제로 복구에 성공한 것을 구분하고, 테스트 결과에 대한 객관적인 증빙을 확보하는 과정도 쉽지 않았다.

## 해결 과정

먼저 Docker Compose를 이용해 서비스 실행 환경을 구성하고, GitHub Actions와 AWS Systems Manager를 활용하여 배포 과정을 자동화하였다.
배포 이후에는 AWS 서버에 직접 접속하여 Docker 컨테이너 상태와 로그, API 응답, Health Check 결과를 점검하였다. 이를 통해 배포 성공 여부뿐 아니라 실제 서비스가 정상적으로 동작하는지도 확인하였다.
오류가 발생한 경우에는 브라우저에서 문제를 재현하고, Backend 로그 및 관련 코드를 확인하여 원인을 구분하였다. 이후 수정된 코드를 배포하고 동일한 조건에서 다시 테스트하여 문제가 해결되었는지 검증하였다.
특히 관리자 요청 재처리 기능은 동일 요청을 두 차례 실행한 뒤 세 번째 요청이 제한되는지 직접 확인하였다. 일반 이용자의 관리자 대시보드 접근 차단과 AI 챗봇의 권한 변경 요청 차단도 실제 운영 화면에서 검증하였다.
최종적으로 테스트 대상 63건이 모두 PASS 판정을 받았으며, 범위에서 제외된 3건은 별도로 구분하여 테스트 결과와 증빙을 정리하였다.

## 배운 점

이번 프로젝트를 통해 배포에 성공하는 것과 서비스를 안정적으로 운영하는 것은 서로 다른 문제라는 점을 배웠다.
이전에는 서버에 애플리케이션을 실행하고 외부에서 접속할 수 있으면 배포가 완료되었다고 생각하였다. 하지만 실제로는 컨테이너 상태와 서비스 응답, 사용자 기능, 장애 발생 시 대응 방식까지 확인해야 한다는 것을 알게 되었다.
또한 CI/CD 자동화가 개발과 배포 과정의 반복 작업을 줄여 주지만, 자동 테스트만으로 모든 문제를 발견할 수는 없다는 점도 체감하였다. 자동 테스트와 실제 운영 환경에서의 수동 검증을 함께 수행하는 것이 중요하였다.
장애 복구 측면에서는 오류 감지, 서비스 지속, 수동 복구, 자동 복구를 구분하여 평가해야 한다는 점을 배웠다. 단순히 오류가 발생하지 않는 시스템보다 오류가 발생했을 때 원인을 파악하고 안전하게 대응할 수 있는 시스템을 만드는 것이 중요하다고 느꼈다.
무엇보다 이번 프로젝트는 개발한 기능을 실제 사용자가 이용할 수 있는 서비스로 연결하고, 그 동작을 끝까지 검증하는 경험이었다. 향후 프로젝트에서도 배포 자동화뿐 아니라 모니터링, 장애 대응, 테스트 증빙까지 고려하여 서비스를 구축하고자 한다.
